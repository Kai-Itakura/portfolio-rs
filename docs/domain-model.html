Project・技術・作品のドメインモデル

Stack パネル・Timeline・作品の元データになる型と、そこから表示のときに計算する値の関係。案件と技術の正は転職活動用の別システム、案件の公開状態と作品の正はこのサイト。v1 ではデータをコードに直接書く。用語は CONTEXT.md を見ること。

決定決めた・実装済み 提案おすすめを出して、返事待ち 未決まだ議論していない 計算保存せず、表示のときに導く

読み取り側：案件と技術

このサイトは別システムのデータを読むだけ。実務の案件も個人開発も別システムから届く。v1 はコードに書いたデータを「一覧を返す関数」の裏に隠し、API ができたら関数の中身だけを差し替える。

structProjectDetails種類によらず持つ項目
  • id: ProjectId提案別システムの ID は ULID。API との照合に使う。
  • title: String決定
  • description: String決定
  • period: Period決定実務の案件も個人開発も持つ。
  • tech_stack: HashSet<TechnologyId>決定ID の集合で参照する。同じ技術の重複を型で防ぐ。順序は持たない（並べるのは QueryService の仕事）。TechnologyId に Hash が要る。
  • publication: Publication決定このサイトが持つ項目。同期は書き換えない。

表示のときに計算する値

件数もゲージも、案件と技術からいつでも導ける。保存すると元のデータと食い違う余地が生まれ、ゲージは最大値が変わるたびに全行が変わるので、DB には置かない。

Stack パネルの 1 行計算
  • 件数tech_stack に含む、公開している案件の数
  • ゲージ7 マス。最大値はすべての技術の中で最も多く使われた技術の件数（全カテゴリ共通）。
  1. 件数が多い順
  2. 最後に使った時期が新しい順
  3. 使い始めた時期が新しい順
  4. 名前順

数えるのは公開している案件だけで、作品は数えない。個人開発を 2 と 3 で最も古い扱いにする規則は、個人開発が期間を持つようになったので見直す（未決）。

Timeline の 1 項目計算
  • 対象公開している案件（実務・個人開発とも）
  • 見出し・説明title / description をそのまま
  • 日付2023.01 - 2023.06（6ヶ月）Period から導く。継続中は「2026.07 - 現在」で長さなし。

このサイトが持つもの：公開状態と作品

案件の公開状態と作品は、このサイトが書き込むデータ。どちらも Project 集約の中に持つ。同期は別システムから届く項目だけを書き換え、案件を消さない。Cloud Run のファイルシステムは揮発性なので、管理画面を作る時点で DB とオブジェクトストレージが要る（ADR 0001）。

enumPublication案件の公開状態
  • Published決定年表・使用件数・作品として見える。
  • Unpublished決定
  • RemovedUpstream決定別システムから消えた案件。作品ごと残し、最初から無かったものとして二度と公開しない（publish が失敗する）。このサイトで消せるのはこの状態の案件だけ（ensure_deletable が検査する）。
entityWork作品（個人開発の中に持つ）
  • PersonalProject.work: Option<Work>決定実務の案件は作品を持てず、個人開発 1 つに作品は 1 つまで。どちらも型で守る。
  • 公開していない個人開発にも足せる決定作品は、個人開発を公開するまで見えない。別システムから消えた案件には足せない。PersonalProject::add_work が検査する。
  • 技術スタックは持たない決定持ち主の個人開発の技術スタックをすべてそのまま見せる。
  • 個人開発が非公開なら作品も見せない決定
  • スラッグが重複しないv2
  • 並び順が一意v2
  • 画像はストレージの URL で配信v2asset! はコンパイル時のパスしか受け付けないため。
