# 作品データは本文だけ Markdown、メタと画像は Rust の定数

1 作品の情報が `content/<slug>.md` と `src/works.rs` の 2 箇所に分かれている。
これは `asset!` がコンパイル時にリテラルのパスを要求する（`const Asset = asset!("...")`、
バンドラはコンパイル済みバイナリを走査してアセットを見つける）ため、
**画像パスを実行時にパースしたデータから渡すことが原理的にできない**という制約による。
散文はファイルで編集したいので Markdown に残し、画像を含むメタ情報は Rust 側の定数に置く、
という分担にした。本文は `include_str!` でコンパイル時に埋め込み、描画時に Markdown を
HTML 化して `Unescaped` で `view!` に流す。実行時のファイル I/O は無い。

## 考えた選択肢

- **全部 Rust の構造体にする** — 型は完全に付くが、日本語の散文を Rust の文字列リテラルで
  持つことになり、編集性と diff の読みやすさが落ちる。
- **全部 Markdown のまま実行時にパースする** — 移行元にいちばん近いが、画像だけは結局
  Rust 側に slug → `asset!` の対応表を持つことになり、1 作品の情報が分裂したうえに
  対応のずれをコンパイラが検出できない。
- **採用案（ハイブリッド）** — 分裂は避けられないので、分かれる境界を
  「散文 / それ以外」という説明のつく線に引いた。`include_str!` はファイルが無ければ
  コンパイルエラーになるので、対応のずれはビルド時に分かる。

## 引き継ぎ

管理 UI（Markdown エディタ + 画像アップロード）は v2 として切り離した。
v1 を静的に保つのは、Cloud Run を `min-instances=0` で運用する前提と両立しないため
（コンテナのファイルシステムは揮発性で、アイドルでインスタンスが破棄されると
アップロードしたファイルが消える）。v2 では画像と本文の置き場を外部ストレージに移すが、
`content/*.md` と Markdown の描画経路はそのまま再利用できる。
変わるのは本文のバイト列の出所（`include_str!` → ストレージ）だけになる。
